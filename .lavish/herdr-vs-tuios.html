What drover asks of the multiplexer

Every four seconds it lists agents on each machine. A status change becomes a Discord reaction. blocked posts the screen. A finished Claude turn is read from the transcript, not from the pane.

What would actually get better

These three are in tuios’s own protocol. herdr can already push status changes (events.subscribe); drover just does not listen. The inbox and the queue are the new pieces.

New

Typed inbox

One list across sessions and linked hosts: approval, question, plan, mail, error, finished turn, resume. A summary is already one line, credentials masked, 160 bytes. reply-approval answers a held permission without keystrokes into the pane.

drover today dumps the pane screen into the thread and cannot tell an approval from a question.

Either side

Push, not a 4s poll

tuios subscribe streams attention and agent-state. List the inbox, then subscribe with its sequence, and a gap means list again.

herdr already has the same event socket. Switching multiplexers is not required to stop polling.

New

Prompt queue

A Discord message that arrives mid-turn waits in the daemon and is typed once the agent has been idle for a second. If the agent does not take it, it is marked stalled and never typed twice.

The queue dies with the daemon. It is not a journal.

The herdr shim is real, and it misses drover

Inside a tuios pane, HERDR_ENV=1 and HERDR_BIN_PATH is a link named herdr. It answers herdr 0.9.3, protocol 22, and prints herdr 0.9.3+tuios. A real herdr on PATH is left alone, and it refuses to start inside that pane.

Real, and not why to move drover

More harnesses

Hooks for Claude, Codex, Cursor, opencode, Pi, Gemini, Copilot, and others, plus screen rules when a hook is missing. drover already starts the five you use. Detection does not replace the transcript reply.

Pane grants

An agent pane can be limited to read, write, or fan. admin does not include answering a prompt. drover’s trust model is still “a Discord message is a keystroke.” Grants do not change that.

Work from the other machine

tuios worktree pull HOST:SESSION copies commits and uncommitted work home. Hosted panes keep the process on meerkat and the window here, and they die if the link stays down past a ten-minute grace. Answering prompts across hosts is off by default.

Fleets, MCP, web, tmux

tuios fan starts the same prompt in several worktrees. There is an MCP server, a tmux shim, and a separate web binary. None of that is the one-thread, one-pane loop drover runs.

Three ways to use this

Stay on herdr

Fits the current desk

Keep herdr-wt, the ~/Developer/repo.branch layout, and herdr --machine. If the four-second poll is the itch, subscribe to herdr’s events from drover. That is a change inside src/main.rs, not a new multiplexer.

Pilot tuios at the desk only

Run a session that drover does not drive. See whether the inbox and ctrlb i replace the Discord reactions you actually look at. Both can be installed. They cannot host each other’s panes: tuios sets HERDR_ENV, and herdr then refuses to start.

Retarget drover after a pilot

Speak tuios verbs: list-attention, subscribe, queue-prompt, reply-approval. Leave the herdr shim alone. Rewrite bin/herdr-wt only if you accept tuios’s worktree directory, or keep creating the checkout yourself and attach. Remotes become tuios hosts, and repos_root has to include ~/Developer because that path is not in the default search list.
